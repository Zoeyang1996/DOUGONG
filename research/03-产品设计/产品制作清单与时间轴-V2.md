## 一、产品结构：一个网页，五个章节

```
榫卯智言 · 保国寺斗拱
│
├─ [0] 入口        钩子 + 四张卡（对应四个知识点）+「一键导览 90s」
│
├─ [1] 千年        斗拱的历史        → 时间轴拖动，斗拱形态随之变化
├─ [2] 名字        各部位叫什么      → 点击识名 ＋「装配游戏」★主游戏
├─ [3] 规矩        斗拱的种类        → 三朵对比 ＋「读法闯关」★副游戏
├─ [4] 不倒        基础受力分析      → 力流 ＋ 杠杆实验 ＋ 拆件实验
│
└─ [VR] WebXR 开关  同一页面进头显   → 仅承载「装配游戏」的沉浸版（可砍）
```

**一句话结构逻辑**：**先知道它是什么（1）、再叫得出名字（2）、再分得清种类（3）、最后明白它为什么站得住（4）。**
这条顺序不能乱——它就是观众认知的顺序，也是产品的教学路径。

## 二、关键设计判断：哪些做游戏，哪些不做

这是最容易做错的地方。**什么都做成游戏 = 什么都做不深。**

| 内容点 | 承载形式 | 为什么 |
|---|---|---|
| ① 历史 | **纯展示**（时间轴 + 形态变化） | 历史是"听故事"，做成闯关会让观众忙着答题、错过故事。只要让**斗拱自己在变**，就足够震撼 |
| ② 部位名称 | **点击识名 + 装配游戏** | 名字天然适合"认—记—用"三段，装配是最有效的记忆手段。**这是产品的主游戏** |
| ③ 种类区分 | **三朵对比 + 读法闯关** | "数跳数、套公式"本身就是一个可判对错的推理过程，天然适合闯关 |
| ④ 受力分析 | **实验式交互**（不是游戏） | 核心快感是"我能弄坏它吗"的探索欲。做成有分数的游戏反而削弱实验感 |
| VR | **WebXR 开关**（同一套代码） | 不做第二个产品。详见第五节 |

**结论**：2 个游戏（装配 + 闯关）+ 2 个非游戏交互（时间轴 + 受力实验）。这是 3 周能做完的最大量。

## 三、制作清单（模块级，可直接派工）

### M0 · 工程底座 ｜ 2 人日
| 项 | 内容 |
|---|---|
| 输出 | Vite 工程、场景骨架、路由（章节切换）、UI 框架、构建脚本 |
| 关键 | 深色底 + 暖木色；`touch-action:none`；`pixelRatio` 上限 2；全资源本地 |
| 验收 | 空场景 60fps；章节可来回切换；窗口缩放不变形 |

### M1 · 模型资产 ｜ 6 人日（关键路径，必须最先启动）
| 项 | 内容 |
|---|---|
| 输出 | 13 种基础构件 → 一朵七铺作柱头铺作（约 50 实例）；补间、转角各 1 朵（简化）；唐/清对比形态各 1 套（仅体量与出跳差异） |
| 关键 | 单位米、栌斗底面中心为原点、命名 `gong_huagong_tiao2_01`、每构件独立材质 |
| 验收 | 单朵 GLB < 3 MB（Draco）；构件数与清单一致；命名 100% 可解析 |

> **13 种基础件**：栌斗、交互斗、齐心斗、散斗、华栱、泥道栱、瓜子栱、慢栱、令栱、下昂、柱头枋、耍头、衬枋头。
> 榫卯只做外观卯口，不建内部结构。

### M2 · 章节①千年 ｜ 2 人日
| 项 | 内容 |
|---|---|
| 交互 | 横向时间轴（西周/汉/唐/宋/明清 5 节点）；拖动或点击节点，中央斗拱平滑过渡到该时期形态 |
| 数据 | 每个节点配 1 张卡：时期 + 一句话特征 + 一个数字（如"斗拱高近柱高一半"） |
| 技术 | 预置 3 套模型形态（唐 / 宋 / 清），`lerp` 缩放与出跳差异；不做骨骼动画 |
| 验收 | 拖动全程无卡顿；切换时无穿模；文字 ≤ 60 字/屏 |

### M3 · 章节②名字 ｜ 5 人日（主游戏）
| 子模块 | 内容 | 人日 |
|---|---|---|
| M3a 点击识名 | 点构件 → 右侧面板：名称、拼音、白话定义、深度解读、来源标注 | 1.5 |
| M3b **装配游戏** | 下方零件盘（6 件/15 件两档）→ **点选零件** → **点选目标位置** → 正确则吸附并"咔"一声，错误则弹回 + 提示 | 3 |
| M3c 完成奖励 | 全部装对 → 整朵合拢、轻微粒子、显示"装配完成 · 用时 xx 秒" | 0.5 |

> **为什么用"点选式"而不是拖拽**：触屏上真拖拽需要持续按压 + 精确落点 + snap 容错，误操作率高，调试成本高。点选两下同样有"装配感"，且老人小孩都能用。**这是省 1.5 天且体验更好的选择。**

### M4 · 章节③规矩 ｜ 4 人日（副游戏）
| 子模块 | 内容 | 人日 |
|---|---|---|
| M4a 三朵对比 | 柱头/补间/转角并排；点其一，另两朵半透明；差异构件高亮 + 一句话说明 | 1.5 |
| M4b **读法闯关** | Step1 定位（选柱头/补间/转角）→ Step2 数跳（点数字，答错播 3 秒逐跳高亮动画）→ Step3 套公式（滑块算 4+3=7）→ Step4 判偷心（答错高亮空位）→ 拼出"七铺作双杪双下昂单偷心造" | 2 |
| M4c 等级阶梯 | 四~八铺作五级，点选看实例（云大寺/晋祠/善化寺/独乐寺/佛光寺） | 0.5 |

### M5 · 章节④不倒 ｜ 4 人日
| 子模块 | 内容 | 人日 |
|---|---|---|
| M5a 力流 | 屋面 → 槫 → 栌斗 → 华栱/昂 → 柱 → 地面，TubeGeometry + 滚动贴图（比 Points 更稳更"流体"） | 1.5 |
| M5b 杠杆实验 | 拖动"屋面重量"滑杆 → 下昂绕支点旋转 → 昂尾上翘压住内柱，接触点高亮 + 文字"昂尾压在梁下，作用如一根斜梁" | 1.5 |
| M5c 拆件实验 | 关掉"横栱"或"栌斗"，屋顶视觉下沉（示意），提示"少了它，这朵斗拱撑不住" | 1 |

> ⚠️ M5 全程必须有固定小字：**"力学示意，非有限元计算结果"**。这是学术诚信底线，也是评委关注点。

### M6 · AI 讲解 ｜ 2 人日
| 项 | 内容 |
|---|---|
| 输出 | 首页选身份（小学生/中学生/建筑专业/亲子）→ 同一构件 4 套文案；一条问答入口；断网兜底 |
| 关键 | 提示词注入事实卡，要求"只改表达不改史实"；每条讲解下方显示"依据：XXX" |
| 验收 | 断网全可用；抽 10 条问答零编造 |

### M7 · WebXR ｜ 2 人日（可砍）
| 项 | 内容 |
|---|---|
| 输出 | 同一页面加 `renderer.xr.enabled = true` + VRButton；进 VR 后只保留装配游戏的沉浸版 |
| 关键 | 固定视点，禁止自由行走（防晕）；关阴影、降贴图；单眼面数 < 80 万 |
| 验收 | 一体机能进、能退、能抓放构件不卡死 |
| ⚠️ | **D14 检查点若 M3 未完成，M7 直接砍** |

### M8 · 集成与交付 ｜ 3 人日
| 项 | 内容 |
|---|---|
| 输出 | 性能报告（stats 截图）、断网验证、4 小时压测、演示脚本、操作手册、录屏 |
| 验收 | 首屏 < 3s；60fps；无死路；连续 4h 不崩 |

**合计：30 人日**（含可砍的 2 人日）。
4 人 × 3 周 × 每周 5 个有效工作日 ≈ 60 人日容量，**留 50% 缓冲**——这是合理的，因为学生实际效率达不到理论值。

## 五、关于 VR：不做第二个产品，只加一个开关

用户提到"甚至加一些 VR 游戏"。**建议用 WebXR，不做独立 VR 应用。**

| 对比 | 独立 VR 应用（Unity/UE） | **WebXR 开关（推荐）** |
|---|---|---|
| 开发量 | 10—15 人日 | **2 人日** |
| 资产 | 需重新导入、重新调材质 | **复用同一套 GLB** |
| 内容 | 要重做一遍交互 | 只做装配游戏的沉浸版 |
| 风险 | 完全独立的技术栈，学生上手慢 | 同一份代码，改几十行 |
| 答辩表述 | "我们还做了一个 VR" | "**一套代码，两种终端**，触屏与头显共用同一资产" |

**代码增量大致是这些**：
```js
renderer.xr.enabled = true;
document.body.appendChild(VRButton.createButton(renderer));
renderer.setAnimationLoop(tick);   // 替代 requestAnimationFrame
// 控制器：controller.getWorldPosition / getWorldQuaternion
```

**VR 版的取舍**：只做"站在一朵斗拱前，用手柄抓构件装回去"这一个场景，5 分钟。不做大殿漫游、不做传送、不做自由行走（防晕）。

**如果省赛/市赛评委不看 VR，这 2 人日就省下来加给 M3。** 建议 D14 后再决定。

## 九、给答辩准备的一句话

> **"我们把斗拱拆成四个问题：它从哪来、它叫什么、它分几种、它为什么不倒。前两个问题用游戏回答，第三个用闯关回答，第四个用实验回答——一套代码，触屏和头显都能跑。"**
