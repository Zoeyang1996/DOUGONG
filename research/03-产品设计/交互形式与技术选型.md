# 交互形式与技术选型

> 用途：确定"做成什么"、为什么这么选、以及三条并行的落地路径
> 结论先行：**主线 = 触屏 three.js 单页；支线 = 5 分钟 VR 高光片段；共用一套模型底稿**

---

## 一、三种形态的可行性对比

| 维度 | A. 触屏 Web（three.js） | B. VR 终端（Quest / PICO） | C. 桌面交互（鼠标键盘） |
|---|---|---|---|
| 开发门槛 | 低（学生可上手） | 高（引擎、性能、晕动症） | 最低 |
| 部署成本 | ≈0（浏览器/一体机） | 需设备（学校已有 VR 设备） | ≈0 |
| 断网可用 | ✅ 完全离线 | ✅ 装包后离线 | ✅ |
| 场馆适配 | ✅ 任意触摸屏 | ❌ 需专用空间 | ⚠️ 桌面式 |
| 答辩记忆点 | 中 | **高** | 低 |
| 学生调试成本 | 低 | **很高**（每次戴头显） | 低 |
| 60fps 可控性 | 高 | 低（移动端 GPU + 双眼渲染） | 高 |

**决策**：
- **A 为主线**，90% 内容在 A 上完成，保证"可交付、可运行、可测试"。
- **B 不做全量**，只做一段 5 分钟、"站在大殿里看一朵斗拱散开再合上"的沉浸片段。它承担的是"哇"的效果，不是知识传递。
- 两者共用同一套 GLB 模型（A 用 Draco 压缩版，B 用原精度版），正好落在申报书"模型资产复用"的表述上。

## 二、触屏交互设计（A 方案）

### 1. 屏幕与硬件假设
- 立式触摸屏，**竖屏 1080×1920 或横屏 3840×2160** 两种自适应，用 CSS `clamp()` + `rem` 布局。
- 屏幕中心高度 1200—1400 mm（成人站立），儿童区 800—1000 mm。
- 倾角 15°—30°。
- 假设无键盘、无鼠标、无网络。

### 2. 手势限定三种（公共设备铁律）
| 手势 | 用途 |
|---|---|
| **单指点击/拖动** | 选中、拖拽旋转模型 |
| **双指缩放** | 拉近看榫卯 |
| **横向滑动** | 切换场景/章节 |

❌ 禁止：长按、双指旋转、捏合+旋转组合、右键、悬停依赖（hover 在触屏不可靠）。

> 所有靠 hover 才出现的信息，在触屏上等于不存在。必须改为"点一下常驻"。

### 3. 界面骨架（建议 5 个场景）

```
[0] 入口       一句钩子 + 「开始」大按钮（≥120px 高）
[1] 定位       大殿半剖/半透明，高亮"我们要看的那一朵"
[2] 读法       四步闯关：定位 → 数跳 → 套公式 → 判偷心
[3] 拆解       爆炸视图 + 单构件点击弹窗 + 受力流线开关
[4] 对比       20 种斗拱族谱 / 与佛光寺、独乐寺横向对比
[5] 历史       三阶段时间轴 + 60 秒短片
```

每个场景**只保留一个主操作**，右上角固定"返回"，底部固定"下一个"。老人在公共屏上最容易迷路。

### 4. 爆炸视图的两种节奏
| 模式 | 效果 | 用途 |
|---|---|---|
| 径向散开 | 各构件沿自身法线向外推出 | 看清"A 压着 B"的咬合关系 |
| 分层平移 | 按"栌斗层 / 华栱层 / 横栱层 / 昂 / 枋 / 耍头"逐层上移 | 看清铺作层数 |

> 推荐**先分层、后径向**：先告诉观众"有几层"，再让他看"每层怎么咬"。
> 参考 ZP-historicBuilding 的两阶段爆炸（0—45% 径向散开，45—100% 收拢为平面清单），这个节奏可以照抄。

### 5. 反馈三通道
- 视觉：选中高亮（描边 + 发光），响应 < 100 ms
- 声音：极轻的木"咔"声（点击构件）/ 榫卯咬合声（装配成功）
- 震动：若有硬件支持；无则用界面脉冲替代

## 三、VR 片段设计（B 方案）——只做这一段

**场景**：观众站在保国寺大殿敞廊下，抬头看前檐柱头铺作。

**5 分钟脚本**
1. 0:00—0:30 环境音（风、鸟、木鱼远声），屋顶压下来，屋檐在头顶。
2. 0:30—1:30 一朵斗拱从梁架中"浮出"到自己面前，1:1 大小。
3. 1:30—3:00 分层拆开：栌斗 → 华栱 → 横栱 → 昂 → 枋。每层散开时出现文字标签（跟随视线的 billboard）。
4. 3:00—4:00 手柄抓取一个"交互斗"，插回原位，听到"咔"声。
5. 4:00—5:00 全部合拢，镜头拉远，屋顶承托完成。字幕：1013—2026。

**技术约束**
- 多边形预算：单眼 < 150 万三角面；draw call < 150。
- 材质：**不用**透明材质与实时反射；用烘焙 AO 贴图 + 单向光。
- 移动方式：**禁止**自由行走（晕动症）。固定视点 + 传送。
- 若时间不足，B 方案可降级为"180° 全景视频 + 少量交互热点"，成本骤降。

| 角色 | 任务 | 交付物 | 验收标准 |
|---|---|---|---|

| 学生 D · 集成测试 | 性能测试、看门狗、断网验证 | 测试报告 | 首屏 < 3s，稳定 60fps，连续 4h 不崩 |

## 五、技术栈建议（vibe coding 友好）

```
构建：Vite（不要 Webpack，配置负担大）
三维：three.js（原生，不上 R3F —— 学生调试心智负担更低）
UI：原生 DOM + CSS（不上 UI 框架，减少依赖）
状态：一个简单的 store 对象（不上 Pinia/Redux）
动画：GSAP（爆炸视图缓动）或 three 自带 Tween（更轻）
模型：GLB + Draco；贴图 WebP + KTX2
离线：Service Worker 缓存全部资产
```

**为什么不用 React Three Fiber**：参考项目用了，但它是给会 React 的人准备的。我们团队是大二学生，原生 three.js 出问题更容易定位。

## 六、风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 触摸屏机器性能差 | 掉帧 | 首屏做设备检测，自动降级（关阴影、降贴图） |
| 断网 | 白屏 | 全部资产本地化 + Service Worker |
| 观众乱点导致卡死 | 展项停摆 | 看门狗：10 秒无操作回首页；每日定时重启 |
| 四人协作版本冲突 | 集成地狱 | Git 分支 + 每周合并；模型单独仓库 |
| AI 接口不可用 | 问答失效 | 预置 50 条高频问答的本地兜底答案 |
| 学术错误被评委指出 | 致命 | 所有知识点标注来源；争议点用"有学者认为" |
