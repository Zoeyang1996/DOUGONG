## 第一章 通用约定

### 1.1 技能怎么讲才算讲清楚

每个技能点按四段说，**不超过 90 秒**：

> 我做了什么（动作）→ 用什么做的（工具）→ 怎么判断做对了（标准）→ 出过什么问题（证据）

第四段最重要。评委听三个人讲"我会用 Blender"不会记住，但会记住"我导出的模型全白，查了三层才找到是程序化节点"。**踩过的坑就是可信度**。

### 1.2 现场演示的三条铁律

| 铁律 | 说明 |
|---|---|
| 只演练过 10 遍以上的动作 | 现场不试新功能。任何"应该可以"的操作都不要做 |
| 每个操作都有 B 方案 | 弹窗报错、加载慢、误触，各准备一句解释 + 一个替代动作 |
| 屏幕上永远有东西 | Blender 提前开好文件，浏览器提前开好三个标签页，不现场找文件 |

### 1.3 每人要提前开好的窗口

| A | 提示词文档（Word）、`data.json`（VSCode）、内容框架表（Excel） |

## 第二章 学生 A · AI 创意策划师

### 2.1 岗位定位

**一句话**：把"要做斗拱科普"这件事，拆成四个人能执行、能验收的清单。

**交付物**：内容框架表、建模清单、四幕分工表、史实红线清单、提示词库。

**上下游**：上游是调研与史料；下游是 B 的建模清单、C/D 的页面清单。

### 2.2 A1 多模态资料检索

| 项 | 内容 |
|---|---|
| 做什么 | 同时用文字、图像、三维、视频四类线索找同一件事的资料 |
| 现场动作 | 无（讲 30 秒即可） |
| 判断标准 | 同一条知识点至少有两个独立信源；图像能对应到具体建筑与构件位置 |
| 常见失误 | 只搜文字，搜到的是二手科普；用自媒体图当形制依据 |
| 追问应答 | "你怎么保证图是你说的那座建筑？" → "先看图里的匾额、斗拱层数，再反查同角度的测绘照片，对不上就不用" |

**讲法（30 秒）**：
"找斗拱资料不能只搜文字。我会同时开四类：一是文献，二是现场照片，三是测绘图纸，四是以图搜图。比如查保国寺的柱头铺作，我先用现场拍的照片搜同类，再拿搜到的图去比对《保国寺修缮报告》里的测绘图，两边能对上，我才把它写进内容表。"

### 2.3 A2 信源分级与史实核验

| 项 | 内容 |
|---|---|
| 做什么 | 给每条资料定级，并设"红线"防止常见错误 |
| 现场动作 | 无 |
| 判断标准 | 一级：测绘报告、学术专著、官方文保档案；二级：博物馆/文物局官网；三级：自媒体、百科——三级只作线索 |
| 常见失误 | 把"始建于"写成"现存"；把重建当成原构 |
| 追问应答 | "你们的内容凭什么说准确？" → 报三条红线（见下） |

**四条红线（必须背下来）**：

1. 法隆寺金堂不能写"公元607年原构"——现存是 7 世纪末重建，607 是始建。
2. 东大寺大佛殿现存是江户时代重建，不是奈良原构。
3. 太和殿现存是清康熙三十四年重建，不是明永乐原物。
4. 保国寺大殿现存重檐是清代所加，宋代原构是单檐——讲"宋构"时必须说清这一点。

**为什么要有这个**：这是评委最容易问倒学生的地方。答对了，整组可信度上一个台阶；答错了，前面讲的全被怀疑。

### 2.4 A3 内容结构化

| 项 | 内容 |
|---|---|
| 做什么 | 把史料拆成三级信息架构，让写页面的人不用再想"讲什么" |
| 现场动作 | 是（切到 Excel 框架表，指三列：卷、页、要点） |
| 判断标准 | 一页只说一件事；每页有图有文有夹注；字数控制在 130—170 字 |
| 常见失误 | 一页塞三个概念；正文写成论文摘要 |
| 追问应答 | "为什么是六卷？" → "现有素材本来就是六组模型，五卷要重编，七卷会拖" |

**讲法（40 秒）**：
"我把内容拆成了三级：第一级是卷，六卷对应六个知识台阶；第二级是跨页，一跨页一个概念，左页放图、右页放文字；第三级是句，每页正文控制在一百三十到一百七十字，考据放到双行夹注里。这样写页面的人拿到表就能直接做，不用再来问我讲什么。"

### 2.5 A4 提示工程

| 项 | 内容 |
|---|---|
| 做什么 | 用四段式提示词让大模型输出可直接用的内容 |
| 现场动作 | 是（展示一条提示词与一次纠错对比） |
| 判断标准 | 四段齐全：角色、约束、样例、反例；同一提示词能稳定产出同结构结果 |
| 常见失误 | 只说"帮我写一段斗拱介绍"；不设字数与禁用词 |
| 追问应答 | "AI 写的东西你怎么改？" → "先看结构对不对，再看事实对不对，最后改语气" |

**四段式模板（现场展示这一条）**：

> 【角色】你是给高中生写展陈说明的文博编辑。
> 【约束】120—150 字；不用"赋能、抓手、闭环"；每个术语第一次出现必须解释；
>         不确定的史实写"据…记载"，不许编年份。
> 【样例】"斗拱不是一种构件，是一组。它从柱头长出来，一层层往外挑，
>         把屋檐的重量接住，再传回柱子。"
> 【反例】不要写"斗拱是中国古代建筑的瑰宝，体现了劳动人民的智慧"——这是空话。

### 2.6 A5 AI 输出校核

| 项 | 内容 |
|---|---|
| 做什么 | 逐条比对 AI 生成内容与红线清单、原始资料 |
| 现场动作 | 无 |
| 判断标准 | 年代、地点、构件名三项零错误；每个数字都能回到出处 |
| 常见失误 | 只看通顺不看事实；把 AI 编的"据《营造法式》记载"当真 |
| 追问应答 | "AI 会不会编？" → "会，而且编得很像。所以年份、数字、引文三类一律回原文核" |

### 2.7 A6 需求转译与验收

| 项 | 内容 |
|---|---|
| 做什么 | 把策划写成 B/C/D 能直接执行的清单，并定义"什么样算做完" |
| 现场动作 | 无 |
| 判断标准 | 每条需求有输入、有输出、有验收标准；改动能追溯到某条需求 |
| 常见失误 | 口头说"做个地球"，对方做出来才发现不是想要的 |
| 追问应答 | "你怎么管另外三个人？" → "不管人，管清单。清单上写清楚交付物长什么样" |

**讲法（30 秒）**：
"我给 B 的建模清单分两类：一类是木构建筑，十二座，每座要外观和斗拱局部；一类是斗拱铺作，只要保国寺柱头这一朵。清单上还写了面数上限和导出格式，不然他做出来我接不进去。"

## 第三章 学生 B · AI 三维资产工程师

### 3.1 岗位定位

**一句话**：把照片和图纸变成能进网页的模型，并且知道为了"能进网页"要放弃什么。

**交付物**：13 个 `.blend` 源文件、12 个 GLB（共 23MB）、一份导出参数说明。

**上下游**：上游是 A 的建模清单；下游是 C 的网页加载。

### 3.2 B1 形制校核建模

| 项 | 内容 |
|---|---|
| 做什么 | 按斗口模数与照片比例建模，不凭想象补细节 |
| 现场动作 | 是（Blender 里旋转柱头铺作，展开大纲视图看构件层级） |
| 判断标准 | 出跳数与照片一致；斗与栱的比例接近实物；构件命名可读 |
| 常见失误 | 比例失真（斗太大、昂太短）；把清式做法套到唐宋建筑上 |
| 追问应答 | "你怎么知道比例对不对？" → "以斗口为基准，其余按倍数推，最后跟同角度照片叠一下" |

**讲法（60 秒）**：
"建模前我先定一个基准：斗口。斗口定了，其余构件都是它的倍数——这是《营造法式》的模数制，也是我能保证比例不走样的原因。建的时候按台基、柱网、铺作、梁架、屋顶的顺序，一层一层往上，这样每一层的标高都能对得上。"

### 3.3 B2 场景清理与归一化

| 项 | 内容 |
|---|---|
| 做什么 | 删掉与建筑无关的东西，把模型缩到统一尺度 |
| 现场动作 | 是（切到 Blender 大纲，展示清理前后物体数量；看包围盒尺寸） |
| 判断标准 | 无相机、无灯光、无地面、无天空；最大边 10 单位；底面落在 y=0；原点居中 |
| 常见失误 | 留着大地面 → 包围盒几百米 → 网页里建筑只有指甲盖大 |
| 追问应答 | "为什么要删配景？" → "包围盒被撑大，取景就全乱。东大寺我一次删了六十四个远处的树石" |

**讲法（50 秒）**：
"模型从 Blender 出来不能直接用。第一步是清场景：相机、灯光、地面、广场、参道、天空穹顶全删。法隆寺那个文件，光地面就有四千多米，不删的话模型进网页只有一小点。第二步是归一化：最大边缩到十个单位，底面落到零，原点居中。这样十二座建筑在网页里是同一个尺度，切换不会一大一小。"

### 3.4 B3 材质还原

| 项 | 内容 |
|---|---|
| 做什么 | 把 Blender 里的程序化颜色，变成 glTF 能认的基色 |
| 现场动作 | 是（打开节点树，指出 Mix / ColorRamp 三个节点） |
| 判断标准 | 导出后瓦灰、木赭、石米三层次可分；无全白、无全黑 |
| 常见失误 | 直接导出 → 全白；用顶点色 → 不同加载器表现不一致 |
| 追问应答 | "为什么不能直接导出？" → "颜色在程序化节点里，glTF 只认基色和贴图，节点它读不懂" |

**这是全场最有说服力的一段技术叙述，按这个顺序讲**：

1. **现象**：第一次导出，十二座全是白的。
2. **排查一**：查 glTF，材质在，但 `baseColorFactor` 是 1,1,1。
3. **排查二**：回 Blender 看节点——颜色来自 Mix 和 ColorRamp，不是基色。
4. **试错**：先把颜色烘到顶点色（`COLOR_0`），结果在三个加载器里，要么全 1 要么全 0，不可靠。
5. **正解**：用 Cycles 烘一遍漫反射，再按每个材质的平均值写回 `baseColorFactor`。
6. **特例**：金属材质没有漫反射色，烘出来是纯黑，所以回退到它原本的基色。
7. **结果**：十二座全部有颜色，且颜色是从模型自己身上取的，不是我猜的。

### 3.5 B4 GLB 导出与 Draco 压缩

| 项 | 内容 |
|---|---|
| 做什么 | 导出成网页能加载的 GLB，并压到可接受体积 |
| 现场动作 | 是（文件管理器看 618MB → 23MB；网页看加载进度条） |
| 判断标准 | 单个 ≤ 7MB；总 ≤ 25MB；Draco 压缩开启；不导贴图与相机 |
| 常见失误 | 导了贴图导致体积爆炸；忘了 Draco，解码器路径又对不上 |
| 追问应答 | "为什么不用 OBJ/FBX？" → "glTF 是网页原生格式，Draco 能把几何压到五分之一" |

### 3.6 B5 性能取舍

| 项 | 内容 |
|---|---|
| 做什么 | 在"好看"和"跑得动"之间做明确取舍，并能说清代价 |
| 现场动作 | 无 |
| 判断标准 | 能报出三个数：面数、体积、加载时间；能说出各自的代价 |
| 常见失误 | 说"优化过了"但说不出优化了什么 |
| 追问应答 | "模型能更精细吗？" → "能，要展 UV 烘贴图，单模型会从 0.7MB 涨到 3—8MB" |

**三个数（背下来）**：

| 项 | 数值 |
|---|---|
| 面数最大 | 太和殿 71 万面 |
| 体积最大 / 最小 | 6.9MB / 0.2MB（北岳庙德宁殿） |
| 总量 | 13 个源文件 618MB → 12 个 GLB 23MB |

### 3.7 B6 问题定位

| 项 | 内容 |
|---|---|
| 做什么 | 遇到"模型不对"时，按层排查而不是瞎试 |
| 现场动作 | 无 |
| 判断标准 | 能说出三类典型故障的现象、原因、解法 |
| 常见失误 | 一上来就改材质，其实是尺度问题 |

**三类故障对照表**：

| 现象 | 原因 | 解法 |
|---|---|---|
| 全白 | 颜色在程序化节点里，glTF 读不到 | 烘漫反射，写回基色 |
| 全黑 | 金属材质无漫反射色 | 回退原基色 |
| 只有一小点 | 场景里有巨大地面/天空 | 清场景、归一化 |
| 位置飘 | 物体离原点很远 | 检查物体中心，把主建筑簇归到原点 |

## 第四章 学生 C · AI 应用开发工程师

### 4.1 岗位定位

**一句话**：把数据、模型和界面接成一个能点得动的网页，并且保证球放大不被切。

**交付物**：act-01 书籍交互、act-02 地球与四级交互、离线打包脚本。

**上下游**：上游是 A 的内容表与 B 的 GLB；下游是 D 的联调。

### 4.2 C1 数据建模

| 项 | 内容 |
|---|---|
| 做什么 | 设计一份 39 条记录的数据结构，让页面按任意维度筛 |
| 现场动作 | 是（VSCode 打开 `data.json`，指字段） |
| 判断标准 | 每条有唯一 id、经纬度、国别、朝代、省份、形制、状态、图片、模型路径 |
| 常见失误 | 字段名前后不一致；坐标写成字符串 |
| 追问应答 | "为什么不用数据库？" → "39 条、只读、要离线，JSON 一个文件最合适" |

**讲解要点（40 秒）**：
"数据结构决定了后面能做什么。我给每条记录定了十来个字段，关键是三个：id 用来定位，经纬度用来打点，province 和 era 用来筛选。有了这三个，同一个地球可以按国家看、按朝代看、按省份看，不用改渲染代码。"

### 4.3 C2 球面坐标与拾取

| 项 | 内容 |
|---|---|
| 做什么 | 把经纬度变成球面上的点，再投影到屏幕上放标签 |
| 现场动作 | 是（点地名签，看红点与标签一起响应） |
| 判断标准 | 标签始终贴着自己的红点；球背面不显示；点击容差 ≥30px |
| 常见失误 | 标签与红点用两套坐标，一转就错位 |
| 追问应答 | "标签怎么跟着球转？" → "每帧把三维点投影成屏幕坐标，标签只是绝对定位的按钮" |

**讲法（50 秒）**：
"地球上的每个建筑就是一个经纬度。我先把它换成球面上的三维点，再投影成屏幕坐标。红点和地名签用的是同一套坐标，所以球一转，它们一起动，不会错位。背面的点要判掉，不然会显示在正面上。"

### 4.4 C3 DOM/WebGL 混合布局

| 项 | 内容 |
|---|---|
| 做什么 | 让三维画布和网页排版共存，且放大后不被裁切 |
| 现场动作 | 是（DevTools 改一个数值，看球与文字的关系变化） |
| 判断标准 | 任何缩放级别下整球可见；左侧说明栏压在球上时层级清楚 |
| 常见失误 | 画布与容器同尺寸 → 一放大就被切平；用 `overflow:hidden` 裁掉 |
| 追问应答 | "为什么球被切？" → "画布比容器小，球超出画布就被裁。我把画布做成比舞台更大，左缘外扩" |

**三个关键决定（讲清这三个就够了）**：

1. 舞台 `overflow: visible`，画布**比舞台更大**：右缘对齐、左缘外扩 `--bleed`。
2. 每帧读舞台边界，换算成画布坐标，交给标签层对齐。
3. "不裁切"是**算出来的**：按屏幕可用半径反推相机最近距离，所有缩放都被 clamp 在这个值。

### 4.5 C4 四级镜头状态机

| 项 | 内容 |
|---|---|
| 做什么 | 四级下钻，每级镜头距离不同，返回逐级回退 |
| 现场动作 | 是（中国 → 唐 → 佛光寺 → 三维，再逐级返回） |
| 判断标准 | 每次点击都有可见的镜头变化；返回回到上一级而不是首页 |
| 常见失误 | 三级四级传了相近的距离，点了像没反应 |
| 追问应答 | "为什么点唐代会转到山西？" → "落点取该朝代所有条目的重心，唐代条目多在山西" |

**讲法（60 秒）**：
"四级不是四个页面，是同一个场景的四个距离。一级全球、二级地区、三级朝代、四级单座。距离不传死数，传层级，按目标半径换算——这样换屏幕尺寸也不会变形。返回也是按层级退，单座退到朝代，朝代退到地区。"

### 4.6 C5 AI 辅助编码与调试

| 项 | 内容 |
|---|---|
| 做什么 | 用大模型写代码、读报错，但自己判断对错 |
| 现场动作 | 否 |
| 判断标准 | 能说出"哪段是 AI 写的、我改了什么、为什么改" |
| 常见失误 | 整段照抄，出错后不知道为什么 |
| 追问应答 | "AI 写的代码你能维护吗？" → "能，因为我要求它先解释思路，再给代码，看不懂的不落地" |

**讲法（40 秒）**：
"我的用法是三步：先让它解释这个问题该怎么解，再让它给最小可运行的片段，最后我自己接进项目。它给的代码我改得最多的是坐标和单位——它经常默认 y 轴向上，而我们是 z 轴。报错的时候我会把报错整段贴给它，但最后一定自己在浏览器里复现一次才算过。"

### 4.7 C6 离线打包与性能

| 项 | 内容 |
|---|---|
| 做什么 | 把整个站点打成能在 U 盘里跑的离线包 |
| 现场动作 | 否（D 演示） |
| 判断标准 | 双击 HTML 就能跑；无 404；无控制台报错 |
| 常见失误 | 只拷 HTML，图片模型没带；`file://` 下模块被拦 |
| 追问应答 | "为什么离线要打包？" → "模块和 fetch 在 file:// 下被拦，必须先合并成一个文件" |

## 第五章 学生 D · 多模态交互设计师

### 5.1 岗位定位

**一句话**：让"看"变成"做"——设计一局能拼、能错、能赢的游戏，并证明它没坏。

**交付物**：act-03 装配游戏、act-04 原型、四幕联调与离线包。

**上下游**：上游是 B 的构件模型与 C 的页面；下游是现场演示。

### 5.2 D1 交互流程设计

| 项 | 内容 |
|---|---|
| 做什么 | 把"认识斗拱"拆成看—拼—验三段，每段有明确目标 |
| 现场动作 | 否 |
| 判断标准 | 用户不看说明也知道第一步做什么；每段有反馈 |
| 常见失误 | 一上来就拼，用户不知道拼什么 |
| 追问应答 | "为什么是 120 秒？" → "一朵铺作 18 组，熟练后 90 秒能完成，120 秒留了容错" |

**讲法（40 秒）**：
"游戏分三段：开始前给你看完整的实木模型，让你知道目标长什么样；开始后只显示当前这一步的落点，不给你整座半透明模型——那样会泛白，看不清；拼完给结算。之所以这么设计，是因为第一次试的时候整模一直亮着，玩家根本分不清哪一层该放。"

### 5.3 D2 装配玩法与容错

| 项 | 内容 |
|---|---|
| 做什么 | 57 个构件、18 组、顺序校验、超时结算 |
| 现场动作 | 是（现场玩一局，控制在 90 秒内） |
| 判断标准 | 放错顺序拒绝；重复归位忽略；切到后台不延长倒计时 |
| 常见失误 | 顺序校验写成"任意顺序都能放"；计时用 `setInterval` 累加，切后台就错 |
| 追问应答 | "错放了会怎样？" → "拒绝，构件弹回，不扣时间但也不给分" |

**技术细节（被问到才说）**：
- 18 组是"同层重复的承斗组合"，同组内可任意顺序。
- 计时用时间戳差值，不是累加，所以后台不延长。
- 构件下落用加速动画，停在承口位置。

### 5.4 D3 状态机与单元测试

| 项 | 内容 |
|---|---|
| 做什么 | 把玩法写成状态机，并为每个边界写测试 |
| 现场动作 | 是（终端跑 `node --test`，6 条全绿） |
| 判断标准 | 6 条用例覆盖：超时边界、顺序、重复归位、18 组完成、重开清零、后台延迟 |
| 常见失误 | 只测"正常流程"，边界全靠手点 |
| 追问应答 | "游戏也要写测试？" → "玩法就是状态转移，状态错了玩家就卡住，比页面更难查" |

**这是 D 最硬的一张牌**：高职组里很少有学生给游戏写单元测试。讲的时候把终端输出投出来，绿色六个勾，比说十句"我做了测试"都管用。

**讲法（50 秒）**：
"玩法本质是状态机：待放、已放、选中、结算四个状态。状态错了玩家就会卡住，而且很难复现。所以我把判断逻辑抽成一个纯函数，用 Node 自带的测试跑。六条用例，覆盖超时那一秒、放错顺序、重复放同一件、十八组拼完、重开清零，还有切到后台再回来时间对不对。现在六条全过。"

### 5.5 D4 程序化材质

| 项 | 内容 |
|---|---|
| 做什么 | 不用贴图，用代码生成木纹与年轮 |
| 现场动作 | 否 |
| 判断标准 | 木纹沿构件长度方向；端面有年轮；构件之间有细微色差 |
| 常见失误 | 所有构件一个色，像塑料；贴图拉伸 |
| 追问应答 | "为什么不用贴图？" → "要离线、要体积小。程序化生成不占资源，还能按构件方向对齐" |

### 5.6 D5 可用性测试与热区

| 项 | 内容 |
|---|---|
| 做什么 | 用真实用户试，按现象改，不按感觉改 |
| 现场动作 | 是（拉窄窗口，展示布局从三栏变纵向） |
| 判断标准 | 热区 ≥44px；窄屏无横向滚动；误触可撤回 |
| 常见失误 | 只在自己电脑上试；热区按视觉大小做 |
| 追问应答 | "怎么发现的问题？" → "让人真点。有人点地名签没反应，才发现容器设了 `pointer-events:none`" |

**真实案例（讲这个）**：
"地名签一开始只能点红点，点文字没反应。我以为是热区太小，后来查样式才发现，标签容器的 `pointer-events` 是 `none`，子按钮没单独开放——文字根本点不动。改完之后热区做到 44 像素高，红点拾取容差也放宽到 30 像素。"

### 5.7 D6 联调与交付

| 项 | 内容 |
|---|---|
| 做什么 | 四幕串起来，打成离线包，在目标设备上跑通 |
| 现场动作 | 是（双击离线包 HTML，直接进入地球） |
| 判断标准 | 双击即可运行；无网络也能翻页、转球、开模型、玩游戏 |
| 常见失误 | 只在自己电脑能跑；忘记带模型目录 |
| 追问应答 | "现场断网怎么办？" → "本来就按离线做的，不依赖网络" |

**离线包检查清单（D 上台前必过一遍）**：

| 检查 | 做法 |
|---|---|
| 目录完整 | HTML 与 `assets/` 同层，缺一不可 |
| 双击可开 | 直接双击 HTML，不是拖进浏览器 |
| 模型能开 | 点一座有三维的建筑，等模型出现 |
| 游戏能玩 | 玩满 120 秒，看结算 |
| 换机可跑 | 拷到另一台电脑试一次 |
| 默认浏览器 | 若被 IE 内核接管，右键"打开方式"选 Chrome |
